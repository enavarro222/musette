# Architecture

## Principles

1. **Rides are never lost.** A ride is acknowledged to the device only after it has been downloaded, verified (`fit::verify`: header + CRC) and stored. Order: download → verify → store → acknowledge.

   ![Fetching rides: list, skip the rides already kept, then for each new ride download, verify, store, and only then acknowledge](diagrams/ride-sync.svg)

2. **Local first.** No account, no server. Activities live on the device the app runs on (IndexedDB in the browser, app files on iOS and Android) and are exported as FIT files.
3. **One app, many devices.** The UI shows only what the connected device can do (`Capabilities`).
4. **Explicit actions.** Destructive or irreversible actions (replacing the device's route, deleting a ride) are always confirmed.

## Layers

![Musette architecture: screens and app logic in TypeScript, one Core interface to the Rust crates, through musette-wasm on the web and musette-ffi on iOS and Android](diagrams/architecture.svg)

**One app, three platforms.** The same TypeScript and React code runs in the browser, on Android and on iOS. Screens use `@expo/ui` universal components: real SwiftUI views on iOS, Jetpack Compose on Android, plain DOM on the web. What differs per platform lives in sibling files that the bundler picks (`x.web.ts` for the web, `x.ts` or `x.native.ts` for iOS and Android): the Rust core loader, storage, transports, file picking, dialogs.

**Screens and navigation** (`app/src/app`, `app/src/screens`). Four tabs: Sorties (rides kept on this device, and fetching new ones), Traces (the route library, usable without a device), Compteur (the connected device and its settings, one screen per group) and Projet. Connecting is app-wide: a modal screen (`/connect`), and every screen's header says which device is connected. Screens use only the kit in `app/src/components/ui.tsx` (iOS, Android) and `ui.web.tsx` (web), with the same API. A button's role sets its look: `primary` for the screen's main action (one at most), `secondary` for the others, `danger` to delete or disconnect.

**Finding a Bluetooth device.** The user does not pick a model: one search finds every Bluetooth model, and the device found tells which model it is (`registry.ts`, `modelOf`). iOS and Android list the devices around (`bleScan`); the browser shows its own chooser (`blePick`).

**Drivers are sans-IO.** Rust code encodes/decodes and decides; the host owns the I/O. This keeps the core testable and reusable: the same `protocol-cc600` crate builds into the firmware (`no_std`), the browser (WASM) and the mobile apps (UniFFI), and `driver-bryton` into the app and `musette-cli`.

**The Rust core** (`app/src/lib/core`): the app sees one `Core` interface. The web loads `musette-wasm`; iOS and Android link `musette-ffi` through a React Native module generated by uniffi-bindgen-react-native (`app/modules/musette-native`, its TypeScript API is committed). Both are thin layers over `musette-core`, which holds the logic.

**One session for every device** (`musette_core::Session`). Each driver has its own sans-IO session (`driver_cc600::Session`, `driver_bryton::ble::Session`); `musette-core` wraps them in one: the same requests (connect, list, download, acknowledge, send a route or a file, read and write settings) and the same `Step` back (channels to subscribe, writes, progress, how long to wait, the outcome). Protocols, UUIDs, timeouts, capabilities, settings fields and ride checks are in Rust. The app runs any session with one class, `BleDevice` (`app/src/lib/devices/bleDevice.ts`): it moves bytes, arms the timer the session asks for, and words the failures in French. A model only adds words (`BleModel`: setting labels and groups) and its search profile (`registry.ts`, checked against the session's channels).

**Rust or TypeScript?** Rust for what is shared with something else in Rust (the firmware, `musette-cli`) or decides on bytes: formats, protocols, state machines. TypeScript for I/O, timers, the UI and its words.

**Transports** (`app/src/lib/transport/types.ts`), chosen by `platform.web.ts` / `platform.ts`:

- `GattTransport` — Bluetooth: subscribe to and write the characteristics a session names. Web: `WebGattTransport`. iOS, Android: `BlePlxGattTransport` (react-native-ble-plx). `maxWrite` cuts the writes of channels that allow it (CC600 frames).
- `FileTransport` — device mounted as a drive. Web: `FileSystemAccessTransport`. Not on mobile yet.

## Many devices

Musette aims at as many bike computers and watches as possible (to add one: [adding-a-device.md](adding-a-device.md)). Everything above the drivers is device-neutral:

- **Routes**: the app prepares one route (name, points, climbs); the session writes it in the device's format (OCRT for the CC600, Bryton's plan-trip FIT for a Rider).
- **Settings**: the session gives each setting's description (`SettingField`: bool, number with range, choice, text, writable) and values; the model's `presentSettings` turns them into the settings screen's fields (toggle, number with unit, choice, text, read-only), each filed in one of **Musette's groups** (`SETTING_GROUPS` in `app/src/lib/settings.ts`: Affichage, Sortie, Navigation, Capteurs, Sons, Énergie, Système), so the settings screen is organised the same for every device and knows none of them. `writeSettings` gets only the changed values; the session checks them all before sending any.
- **Rides**: FIT, the common format, checked by the session before the app gets them, acknowledged only once stored.

For the CC600, keys, ranges and choices come from `settings-cc600` (`FIELDS`, what the device accepts); the app adds labels and groups (`cc600Settings.ts`, a test checks every key has them).

## CC600 protocol (draft)

Defined in `crates/protocol-cc600`. Frame: `ver | op | seq | len (u16 LE) | payload | crc16`. Requests (`op < 0x80`) come from the app; responses reuse the request's `seq`. BLE: one service, an RX characteristic (write without response) and a TX characteristic (notify); frames may span several GATT packets.

Main flows:

- `Hello` → `DeviceInfo`
- `ListActivities` → `ActivityEntry`* → `EndOfList`
- `GetSettings` → `Settings` (the settings file, `key=value` lines); `SetSettings` (changed lines only) → `Ok` or `Error(BadSetting, key)`, all or nothing
- `ReadActivity(id, offset, max)` → `ActivityChunk` (repeat) → app verifies → `AckActivity`
- `TransferBegin(kind, size, crc)` → `TransferReady(next, window)` → `TransferChunk`* (⇄ `TransferAck`) → `TransferEnd` → `Ok` (replaces the active route, or the map of the route). Kinds: route, map.

### File transfer (`protocol_cc600::transfer`)

Routes and maps are a few hundred KB over BLE (5–20 KB/s from a browser), so the transfer is **resumable** and **flow-controlled**:

- The device keeps the partial file and its running CRC. A new `TransferBegin` with the same kind, size and CRC answers `TransferReady` with `next > 0`: the app continues from there.
- The app pipelines chunks (write without response) up to `window` bytes; the device acks every `window/2` bytes and at the end.
- A chunk that is not the expected one is not written; the device sends one `TransferResend(next)` and the app resends from there. `TransferAck` only means progress: with chunks in flight it is always behind what the app sent.
- Silence (lost ack or lost last chunk): the app sends `TransferBegin` again and the device says where it is.
- `TransferEnd` checks size and the CRC of the whole file, then commits atomically. `BadCrc` drops the partial file.
- Errors (`Op::Error`, one byte): bad request, no space, no transfer, incomplete, bad CRC, busy (ride recording), storage.
- `Receiver` (device) and `Sender` (app) are sans-IO state machines, tested together with lost chunks and cuts. `driver_cc600::Session` drives the `Sender` (and the silences); `driver_cc600::sim` is a CC600 in memory around the `Receiver`, for the tests and the app's demo.
